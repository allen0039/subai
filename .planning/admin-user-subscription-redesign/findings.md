# 调研记录

## 现有实现差距

- `members` 已包含用户名、角色、状态和密码哈希，成员更新接口也能修改密码。
- 登录服务当前强制要求角色为 `admin`，普通用户不能登录管理界面。
- 前端成员编辑表单未暴露用户名和密码修改入口。
- `clients` 仍是独立实体，`api_keys.client_id` 可选关联客户端，与新需求不符。
- 当前 Key 直接通过 `key_routes` 绑定单个账号或账号组，没有套餐实体，也没有用户订阅关系。
- 当前账号组只有成员和权重，管理体验依赖手工输入 UUID。
- 现有预算策略能作用于成员、Key、账号和组，可复用账本与预留结算能力，但不等同于可售卖/可分配的套餐模板。
- OAuth 与手工 Token 接入已经存在，可作为新的上游账号引导流程基础。

## 用户确认

- 一个用户可以同时拥有多个套餐。
- 用户创建 Key 时自行选择本次 Key 使用的套餐。
- 其余业务规则采用上一轮提出的默认值。

## 参考实现核对

- CPA Management Center 将上游管理拆为凭证文件与 OAuth 流程，支持发起授权、轮询状态、回调提交、凭证搜索/分页、模型可用性与重新授权；本项目可借鉴其向导式交互，但继续使用现有加密数据库存储，不照搬文件存储。
- Sub2API 将“套餐配置”和“用户订阅实例”分开：套餐/组保存日、周、月限额，用户订阅保存起止时间、状态、各周期窗口与已用额度。
- Sub2API 管理端具备订阅分配、批量分配、延期、额度重置、撤销和恢复等操作，可作为管理工作流参考。
- Sub2API 的 Key 创建支持选择分组；本项目应改为选择用户拥有的具体订阅实例，以支持同名套餐的独立有效期和额度账本。
- 公开 issue 显示“用户分组改变后旧 Key 仍能访问旧池”是现实风险。本项目必须在每次请求鉴权时动态校验 Key → 用户订阅 → 套餐版本/账号池的当前有效关系，不能只在 Key 创建时复制权限。
- 参考实现使用浮点字段保存部分美元数据；本项目继续遵循既有 `NUMERIC(30,12)` 定点金额规则，不采用浮点累计。

## 目标模型决策

- 套餐拆成 `plans`（稳定身份）和 `plan_versions`（不可变配置快照）。编辑已发布套餐会创建新版本，既有订阅不被静默改变。
- 用户拿到的是 `user_subscriptions` 订阅实例；同一用户可同时拥有多个不同套餐订阅。默认不允许同一用户同时拥有两个相同套餐的有效订阅，历史续订保留。
- `api_keys.user_subscription_id` 必填。用户创建 Key 时选择自己的有效订阅实例，不直接选择账号池。
- 套餐版本通过 `plan_pool_bindings` 绑定多个账号池；池成员变化实时影响候选账号，套餐版本的池列表不随意漂移。
- 用户额外获配的单账号或账号池分别记录为显式授权，路由范围为“所选套餐的池 + 用户有效额外授权”的并集。
- 额度属于订阅实例而不是用户总账户；同一订阅下的所有 Key 共享该订阅的日/周/月额度。
- Key 的模型、并发与有效期只能收窄套餐/订阅边界，不能扩大。
- 每次请求在审核前后都动态校验用户、Key、订阅、套餐版本和路由授权，防止权限漂移。
- 现有 `budget_policies`/`budget_periods`/`reservations`/`usage_ledger` 继续作为原子预算账本，扩展订阅作用域和月周期。
- `account_groups` 在产品和接口层改称账号池；数据库是否物理重命名放在兼容清理阶段，避免一次性扩大迁移风险。
