# WebUI 重构修复与优化计划

## 目标与边界

目标是在不改变既有认证、权限、哈希路由和管理操作语义的前提下，把 WebUI 逐步升级为“控制塔”式运营台与个人台。

本计划不将静态演示数据、没有后端接口的设置项或未经授权的数据暴露作为正式功能发布。每个阶段必须保持 `npm ci && npm run build`、`go test ./...` 通过。

## 当前基线（已完成）

- 已恢复原有管理员/会员分流、登录会话、哈希路由和所有既有资源页。
- 已完成分组导航、可折叠侧栏、顶栏、主题记忆、状态快照卡片及弹窗的基础键盘支持。
- 状态页只消费现有 `/api/admin/status`，不伪造趋势或成本数据。
- 前端与后端测试在干净依赖安装后均通过。

## 阶段与交付

| 阶段 | 内容 | 主要改动 | 验收标准 | 预估 |
|---|---|---|---|---|
| P0 | 收敛原型与发布基线 | 清理或明确隔离未接入的 mock 页面、重复组件和“已完成”但不真实的文档；补 CI 前端构建检查 | 干净安装可构建；正式入口没有 mock 数据、无失效路由或虚假设置 | 0.5–1 天 |
| P1 | 设计系统与 Shell 完整化 | 将现有 CSS 统一为 token；补完整亮色主题、移动端抽屉、侧栏折叠记忆、页面标题/摘要规范 | 管理端和个人端在 360px、768px、1440px 下可用；暗亮主题均可读、无水平溢出 | 1–1.5 天 |
| P2 | ResourcePage v2 | 资源页统一为“摘要 → 工具栏 → 表格 → 分页”；补空态、骨架、读抽屉与写弹窗；按资源增加服务端筛选 | 既有创建/编辑/撤销/OAuth/复核流程保持可用；筛选不拉取全量分页数据 | 1.5–2 天 |
| P3 | 指标与搜索数据契约 | 新增有权限边界、可索引、可缓存的仪表盘、全局搜索、事件增量接口及测试 | 任意指标都能追溯口径；搜索不返回密钥/令牌；查询量不随历史数据线性恶化 | 1.5–2 天 |
| P4 | 真实控制塔与账号配额 | 接入统计卡、趋势图、账号健康矩阵、双环配额组件、账号详情抽屉和事件流 | 只显示 API 返回的实时/聚合数据；快照缺失或过期有明确状态；图表范围和时区可见 | 1.5–2 天 |
| P5 | 会员个人台 | 联合查询订阅、密钥、账号池，重做概览和用量摘要 | 不泄露账号身份、出口、凭据或其他成员数据；无 N+1 请求 | 1–1.5 天 |
| P6 | 可用性、验证与发布 | 无障碍、失败重试、取消陈旧请求、视觉回归、镜像和 Oracle3 灰度更新 | 键盘可完成核心流程；前后端测试、Docker 构建、健康检查与部署后冒烟通过 | 1–1.5 天 |

总预估：8–11 个工程日；P3 是 P4 与 P5 的前置条件。

## P0：发布基线收敛

1. 审核 `web/src/components/`、`web/src/pages/`、`web/src/styles/` 中未接入正式入口的原型。
2. 对每个文件做二选一：
   - 与正式架构合并，补真实 API 和测试；或
   - 从待发布源码与用户文档中移除，保留设计方案即可。
3. 修正文档中与实际不符的声明：Tailwind 版本、Router、完成状态、页面清单与依赖清单。
4. 在 CI 中固定执行 `npm ci && npm run build`，避免本机残留依赖掩盖类型错误。

## P1：视觉与交互规范

- 使用 CSS Custom Properties，保留零新增运行时依赖。
- 主题值只通过 token 替换；不得在业务组件继续增加硬编码深色值。
- 状态表达必须同时包含文字、图标或徽章，不能只依赖红黄绿。
- 动画遵循 `prefers-reduced-motion`；侧栏与抽屉的焦点、Esc、返回焦点行为必须一致。
- 小屏采用抽屉导航，不把 240px 侧栏压缩后长期占据内容宽度。

## P2：ResourcePage v2 细则

- `ResourcePage` 增加可选 `summary`、`filters`、`rowDetail`、`emptyState` 配置，而不是为每一页复制页面代码。
- 筛选字段按资源定义：例如账号使用状态/池/套餐，审计使用决定/时间，账本使用时间/成员；不强制每页都有筛选。
- 搜索和筛选参数由服务端处理，保持 `limit` 上限、允许字段白名单与索引策略。
- 抽屉只承载“读”和低风险刷新；创建、编辑、撤销等写操作保留显式确认的弹窗。
- 所有加载请求使用 `AbortController` 或请求版本号，避免切换页面后的陈旧响应覆盖当前数据。

## P3：后端数据契约

### 仪表盘

新增 `GET /api/admin/dashboard?range=24h|7d`，返回：

- `as_of`、服务器时区、数据延迟和聚合粒度；
- 当前 readiness、活跃/unknown 请求、账号状态计数；
- 固定时间桶的请求数、成功数、失败数、延迟和成本（只有具备可靠成本数据时返回）；
- 账号配额覆盖数、过期快照数和按状态计数。

数据库查询必须使用时间范围、聚合和索引；不能在每次页面刷新时扫描全部请求、账本或审计历史。

### 全局搜索

新增 `GET /api/admin/search?q=...&types=user,key,account,pool`：

- 最少查询长度、类型白名单、每类/总结果上限和防抖；
- 仅返回展示所需的 ID、标题、状态、跳转目标；
- 必须复用管理员权限校验，不返回密钥、访问令牌、刷新令牌、代理凭据或敏感备注。

### 事件增量

在管理事件和审核事件上提供安全的 `after_id` 或 `since` 游标。前端只拉取增量，失败后显示“最后更新时间”，不得把短轮询伪装成实时流。

## P4：控制塔与额度体验

- `QuotaRing` 输入以现有快照的 `used_percent`、窗口长度、重置时间和同步时间为准，不用“小时数”冒充百分比额度。
- 组件需要 `unknown`、`stale`、`healthy`、`warning`、`critical` 五种明确状态；未知数据不能渲染为 0%。
- 趋势图、Pipeline 和健康矩阵仅消费 P3 的接口；无法观测的链路阶段显示“不提供指标”，不推测健康度。
- 账号详情抽屉须支持刷新额度、加载中、刷新失败和最近同步时间；写操作仍走确认弹窗。

## P5：个人台数据边界

- 优先提供单个 `GET /api/admin/me/overview` 联合视图，代替多个页面并发拼接与 N+1 请求。
- 可返回当前成员自己的订阅状态、密钥计数、预算/用量摘要和抽象的池可用性；禁止返回账号标签、出口、代理、其他成员信息或任何凭据。

## P6：质量门槛与发布

1. 单元测试：图表数据转换、额度状态、日期/时区、搜索参数、权限过滤。
2. 组件测试：路由/角色分流、抽屉与弹窗键盘操作、空/加载/错误态、主题切换。
3. 集成测试：dashboard/search/event cursor 的权限、上限、无敏感字段和查询边界。
4. 手工视觉验收：登录、管理员仪表盘、账号创建与额度刷新、审核复核、会员概览；三种视口与两种主题。
5. 发布：本地 `make lint && make test && cd web && npm run build`，再按 `docs/RELEASE.md` 发布 Docker Hub 镜像并更新 Oracle3；部署后检查 `/healthz`、容器状态、版本与目标提交。

## 风险与决策点

| 风险 | 处理方式 |
|---|---|
| UI 先于数据能力 | P4/P5 不使用静态数字；P3 未完成时只交付真实状态快照与资源页改造。 |
| 视觉改造造成业务回归 | 每阶段在现有 hash 路由和 API 上渐进接入，禁止用独立演示路由替换生产入口。 |
| 亮色主题局部不可读 | 用 token 审计和双主题截图作为 P1 验收，而非只切换根背景。 |
| 全局搜索泄露敏感信息 | 后端结果 DTO 白名单、权限测试和日志脱敏。 |
| 仪表盘性能劣化 | 有界范围、预聚合/缓存、索引和查询性能测试。 |

## 建议执行顺序

先完成 P0，再按 P1 → P2 → P3 → P4/P5（可并行）→ P6 执行。任何阶段若未通过质量门槛，不进入 Docker 发布或 Oracle3 更新。
