# SubAI 基于 sub2api 整体替换实施方案

日期：2026-09-14。状态：方案完成，尚未实施或部署。

## 1. 已确认目标

完整采用 Wei-Shaw/sub2api 的代码、架构、前后端、数据库模型、功能和运行方式。唯一产品定制是将 SubAI 现有 GPT 上游账号登录/授权方案接入并替换上游对应路径。平台用户注册、管理员登录、其他供应商认证、调度、计费、额度与运维均沿用 sub2api。

旧项目仅作为 GPT 授权来源和历史数据来源，不作为新运行时依赖。旧界面、审核、计费、模型规则等自定义实现不继续移植。仓库、域名和自建镜像所需配置属于运行适配，不改变上游产品行为。未来二次开发单独排期。

“全部功能”以固定源码版本的可交付功能为边界；配置开关、外部插件、支付、邮件和供应商凭证等依赖在清单中注明。源码存在不等于已配置或已实测，不能据此声称所有外部服务已可用。

- SubAI 当前提交：`1b6d901f75da6046c096fa5909d8a2cab0357c79`，调研开始时工作区干净。

- 当前项目：Go + React + PostgreSQL；上游：Go + Vue/TypeScript + PostgreSQL + Redis。
- 现有授权主体：`internal/accounts/oauth.go`；HTTP 接入：`internal/admin/audit_handlers.go`、`internal/admin/routes.go`、`internal/server/server.go`；前端入口：`web/src/App.tsx`。
- 上游接入点：`backend/internal/service/openai_oauth_service.go`、`backend/internal/handler/admin/openai_oauth_handler.go`、`backend/internal/repository/openai_oauth_service.go`、`backend/internal/service/token_refresher.go`、`backend/internal/server/routes/admin.go`。

- 当前发布文档表明推送 main 会发布镜像。新实现采用隔离分支和环境，完成验收后才进入正式发布。
- 上游 LICENSE 为 LGPL-3.0 文本；导入时保留许可证、版权及来源，记录修改，分发时按实际许可履行相关义务。

| 阶段 | 具体工作 | 交付物与通过条件 |

| P1 整体导入 | 在新分支以完整上游树替换运行时代码，保留本仓库 Git 历史；采用 backend/frontend/deploy 结构及锁文件、生成代码、静态资源、测试；归档旧文档；按上游拓扑启动独立 PostgreSQL/Redis | 未改 GPT 授权前的上游基线可构建、启动、完成初始化和基础页面操作；记录上游原有测试失败 |
| P2 GPT 适配 | 提取旧授权协议与交互；用 sub2api 的鉴权、账号仓储、代理和凭证刷新框架承接；改造上游 GPT 授权弹窗；所有对应入口委托同一实现 | GPT 新授权、重新授权、回调提交、过期刷新完整可用；没有重复账号写入或第二套刷新任务 |
| P3 数据处理 | 用旧库副本盘点；优先全新上游 schema；需要保留的数据用一次性导入工具转换，无法无损映射的输出差异报告 | 可重复 dry-run、ID 映射、导入统计和金额/有效期核对报告；旧库不被上游迁移脚本修改 |

| P5 切换准备与上线 | 构建自有不可变镜像；验证备份恢复与回滚；按需停写、最终导入，停止旧账号刷新后切换流量 | 发布清单、回滚记录、上线后调用/usage/刷新健康证据；正式切换是后续执行阶段 |

P0 → P1 → P2 → P4 为主路径；数据结构固定后执行 P3，P3/P4 都通过才进入 P5。当前请求只完成这份方案，不启动这些实施阶段。

## 4. GPT 登录替换的具体边界

### 保留的行为

1. 创建授权会话并生成 OpenAI 登录链接，保留现有 client_id、scope、PKCE、回调配置与必要授权参数。
2. 用户在自己的浏览器完成登录，复制完整 localhost 回调 URL，回填管理台完成授权。
3. 校验回调地址、state、有效期及单次消费；授权会话关联发起管理员及目标账号。
4. 提取 access_token、refresh_token、id_token、账号身份与到期时间；重新授权更新指定账号。
5. 保留原有 GPT refresh token 协议和必要凭证字段回退行为，适配上游刷新框架。

### 与 sub2api 的接法

- 保留上游 Vue 账号管理页面和账号创建/重新授权入口，仅替换 GPT 授权交互与调用；不携带旧 React 页面。
- 将旧授权代码拆分为协议逻辑、短期会话存储和账号持久化适配。短期会话优先接入上游现有基础设施，必须保证过期和原子消费；确需新增存储时只增加 GPT 会话所必需的内容。
- 会话创建、读取、提交接口保留现有路径和字段语义作为兼容入口，使用 sub2api 管理员鉴权；账号 ID 采用上游类型。旧 UUID 如涉及已有数据，通过映射处理，不为了旧 ID 改造全局模型。
- 原公开 `/api/oauth/callback` 如保留，与手动回填进入同一完成逻辑，以 state 关联授权会话；不能要求提供方回调携带管理员登录态。管理员操作接口仍校验权限和会话归属。
- 上游原 GPT 授权入口删除或委托到同一服务，不保留可独立走通的另一套登录实现。API Key 导入、其他平台 OAuth 保持上游行为。
- token 与身份写入 sub2api 原生账号模型；provider/platform、到期单位、账号标识、代理关联、凭证合并及缓存失效逐项核对。不得泄露 token 到响应、日志或迁移报告。
- 自动刷新由 sub2api 原有任务/锁机制统一拥有；适配 GPT 刷新协议，不搬入旧 Manager 的后台生命周期和 account_holds 状态机。搜索全部定时/手动/请求内刷新入口，确保不会绕过统一实现。
- OpenAI handler 同时包含额度查询、额度刷新和其他账号功能，不能整文件删除；这些功能继续使用上游逻辑。授权后也调用上游额度同步与账号缓存更新。
- 不照搬旧实现中的缺陷；必要正确性修复限制在授权边界内，记录与原行为的差异。

GPT 授权数据流：上游管理台 → 当前方案的授权服务 → OpenAI → 回调 URL 提交 → sub2api 账号仓储 → sub2api 调度/转发/计费。刷新由 sub2api 统一调度 → 同一 GPT 凭证适配 → 上游账号仓储。

## 5. 全量功能核对方式

以固定 SHA 自动列出页面、服务端路由、后台任务、数据库迁移和功能开关，形成 `模块 / 上游路径 / 本地路径 / 配置依赖 / 测试证据 / 状态` 矩阵，做到源码覆盖和行为验收分开记录。

本轮源码确认的功能域包括：平台注册/登录和初始化；用户与权限；账号、分组、代理和渠道；API Key；模型配置与模型广场；网关转发和账号调度；usage、计费与订阅；充值、订单、支付、兑换码与促销；邀请/返利；公告、自定义页面与系统设置；风险控制、审计日志、渠道监控与运维；备份和插件管理。最终清单从基线生成，不把此摘要当作穷尽清单。

对支付、邮件、其他供应商和外部插件：保留所有上游源码与配置入口，区分“测试通过”“待配置”“上游基线失败”“实际服务未验证”。不得将缺少凭证的测试跳过写成验收通过。

## 6. 数据策略

新服务使用全新的 sub2api 数据库和 Redis 命名空间/实例，禁止在旧 SubAI 数据库上执行上游迁移；生产现状本轮未连接检查。

如果旧数据不需要延续，最短实施路径是新系统初始化后重新配置并重新登录 GPT，旧库保留备份。如果需要延续，执行以下独立数据迁移；是否保留及范围在数据盘点后由用户确认，不影响 P0–P2 开发。

| 数据 | 建议处理 |
|---|---|
| GPT 账号及代理 | 通过一次性工具将凭证解密后转换为上游要求格式，敏感值只在受控内存中处理；也支持逐账号重新授权；账号 ID 建映射 |
| 用户与密码 | 核对密码哈希算法/参数和身份唯一性；不兼容时走上游重置密码流程；旧登录会话不复用 |
| API Key | 核对明文/哈希存储、前缀、验证算法及绑定语义；不能保证兼容时生成新 Key 并提供客户端替换清单，禁止假定可无损复制 |
| 分组、订阅、有效期与额度 | 按上游模型重建，逐条报告原值/目标值/差异；旧额度不自动等同余额，金额换算规则须明确 |
| 历史账单、usage 与审计 | 优先导出并只读归档；有无损对应才导入历史字段，避免重放历史账单重复扣款；不在新系统中复刻旧计费引擎 |
| 模型价格、规则及系统配置 | 采用上游配置能力；兼容配置按需转换，上游无对应能力的旧定制不移植 |

导入支持 dry-run、批次标识、可重复执行且不重复创建、异常停止和差异报告；在旧库副本演练后才运行最终导入。余额、未结请求、订阅到期时间和冻结状态必须单独核对。

## 7. 验收标准

- 基线：后端构建与 `go test ./...`、上游 lint、unit/integration/e2e 目标按仓库要求执行；前端 `pnpm typecheck`、`pnpm lint:check`、`pnpm test:run`、`pnpm build`。先复现纯上游结果，再判断本地回归。
- 基础设施：全新 PostgreSQL/Redis 初始化、重复启动、升级、重启后账号可用、镜像构建与健康检查通过。
- GPT：首次登录、重新登录、取消/拒绝、错 state、错会话、过期、重放、错误回调地址、同时回填、跨管理员访问、重启中断、token 缺失、刷新失败及恢复、刷新与重新授权并发均覆盖。
- 刷新：不会并发消耗同一个 refresh token；旧结果不覆盖新凭证；保持上游账号停用语义；缓存及时更新；刷新后可继续真实调用。
- 业务：管理员创建用户/分组/订阅/Key → GPT 账号入组 → 客户端调用 → 流式完成/中断/失败 → usage 和扣费 → 仪表盘核对，形成完整证据。
- 全量功能：所有基线功能在验收矩阵中有明确状态；非 GPT 模块无自定义行为差异。集成测试不向生产支付/邮件服务产生真实动作。
- 真实性：必须实测浏览器登录和刷新后调用才可标记 GPT 真实链路通过。没有可用账号时标记待验证，不以 mock 替代。
- 可回滚：演练流量切回旧服务、恢复旧库，以及处理切换后新增账单的步骤。

## 8. 发布与回滚

1. 构建包含 GPT 补丁的自有镜像，使用固定 SHA/tag，不能直接部署上游官方镜像，否则补丁会缺失。
2. 采用上游 Compose 和配置模型，适配自己的镜像、域名、卷、密钥和反向代理；验证升级入口不会用官方二进制覆盖定制版本。升级经固定版本导入、补丁重放、回归测试、自有镜像发布。
3. 保存旧镜像版本、配置和可恢复数据库快照；新服务先用独立测试账号完成演练。
4. 同一个生产 GPT 账号不得由两套系统同时刷新。最终切换前停止旧系统接单和刷新任务，等待在途请求结算，执行最终导入，核对结果后启动新系统接管。
5. 切流后核对错误率、首 token 延迟、账号刷新、队列和扣费。持续授权失败、核心接口不可用、重复扣款或数据对账异常即停止继续放量并启动回滚处置。
6. 新系统尚无业务写入时可以直接切回。已有新增账单或凭证轮换时，先冻结新写入并保存新库，核对消费差额和最新 GPT 凭证，再恢复旧服务；不能只换镜像或直接恢复旧快照，否则丢失账单或使用失效 token。

## 9. 交付批次与后续维护

建议按“纯上游导入”“GPT 授权适配”“数据工具与部署适配”“验收报告”拆分提交，保证每批可审查。维护一份上游 SHA 和定制文件清单，后续只重放 GPT 补丁及必需部署配置。

工作量主要取决于 GPT 适配与旧数据语义转换。先用 P0/P1 的实际构建和测试结果确定工期；全新初始化路径较短，保留原用户/Key/额度的路径额外需要数据演练。当前未跑上游构建测试或真实联调，不承诺固定天数。

实施开始前无须再次讨论整体技术方向；上游版本可按发布记录与测试选择。需要后续明确的是旧数据保留范围；正式上线还需提供具体切换窗口和真实联调条件。上述事项不阻塞隔离环境内的基线导入和 GPT 适配。
