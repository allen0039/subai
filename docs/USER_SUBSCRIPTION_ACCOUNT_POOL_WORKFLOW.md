# SubAI 用户、订阅套餐与账号池重构工作流程方案

版本：v1.0  
日期：2026-09-13  
状态：需求已确认，供实施前评审  
范围：用户体系、登录权限、API Key、上游账号、账号池、套餐订阅、额度与迁移

## 1. 目标与最终使用方式

这次重构把 SubAI 从“管理员为设备配置 Key”的内部工具，调整为“管理员分配资源，用户自助创建 Key”的多用户网关。

最终业务链路为：

```text
管理员录入上游账号
    ↓
将一个或多个账号组成账号池
    ↓
创建套餐版本，并给套餐绑定一个或多个账号池、额度和权限
    ↓
给用户分配一个或多个套餐，形成多个独立订阅实例
    ↓
用户登录，在自己的订阅中选择一个创建 API Key
    ↓
请求使用该订阅的额度，并从该套餐账号池及用户额外授权中选择上游账号
```

“客户端（设备 / Agent）”不再参与任何业务流程。用户可以在任意设备使用自己创建的 Key，系统只按用户、Key、订阅和账号池管理权限及用量。

## 2. 已确认的业务规则

1. 管理员和普通用户都能用用户名、密码登录。
2. 管理员可创建、编辑、禁用用户，修改或重置任意用户密码。
3. 普通用户只能查看自己的订阅、额度、用量和 Key，并修改自己的密码。
4. 一个用户可以同时拥有多个有效套餐订阅。
5. 用户创建 Key 时必须选择一个属于自己的有效订阅。
6. 一个 Key 只能绑定一个订阅；同一订阅可被多个 Key 共享。
7. 同一订阅下的 Key 共享该订阅的额度，不分别复制额度。
8. 套餐支持日、周、月内部美元额度；配置了多个周期时，所有限制同时生效。
9. 套餐还可以限制并发、允许模型、有效期和可创建 Key 数量。
10. 套餐可以绑定多个账号池；账号池可包含一个或多个账号。
11. 管理员还可以直接向用户追加单个账号或账号池；最终候选范围取并集。
12. 账号可同时加入多个账号池。
13. 账号池支持轮询、权重轮询和优先级故障切换。
14. Key 的设置只能比订阅更严格，不能突破订阅限制。
15. 密码变更后撤销该用户的其他登录会话。

## 3. 角色与权限

| 功能 | 管理员 | 普通用户 |
|---|---:|---:|
| 登录、退出、查看本人信息 | 是 | 是 |
| 修改本人密码 | 是 | 是 |
| 创建、编辑、禁用用户 | 是 | 否 |
| 重置其他用户密码 | 是 | 否 |
| 管理上游账号、OAuth 和代理 | 是 | 否 |
| 管理账号池 | 是 | 否 |
| 创建和发布套餐 | 是 | 否 |
| 给用户分配、延期、暂停或撤销订阅 | 是 | 否 |
| 给用户额外分配账号或账号池 | 是 | 否 |
| 查看所有 Key 和用量 | 是 | 否 |
| 查看自己的多个订阅及剩余额度 | 是 | 是 |
| 为自己创建、暂停和撤销 Key | 可代管 | 是 |
| 修改 Key 所属订阅 | 否，采用重新创建 | 否，采用重新创建 |
| 查看上游账号真实信息或凭证 | 仅非敏感信息 | 否 |

额外约束：

- 系统必须始终保留至少一个启用状态的管理员，不能禁用或降级最后一个管理员。
- 管理员重置用户密码后，该用户全部登录会话立即失效。
- 用户修改自己的密码时必须提交旧密码；修改成功后保留当前会话，撤销其他会话。
- 普通用户接口不能通过修改 URL、UUID 或请求体访问其他用户的数据。

## 4. 核心数据模型

### 4.1 实体关系

```text
members
  ├──< user_subscriptions >── plan_versions >── plans
  │          │                       │
  │          │                       └──< plan_pool_bindings >── account_pools
  │          │                                                    └──< pool_members >── accounts
  │          └──< api_keys
  │                  └──< requests / usage_ledger
  │
  ├──< user_account_grants >── accounts
  └──< user_pool_grants >───── account_pools
```

### 4.2 建议新增或调整的表

#### `members`

保留现有表，继续保存用户身份。

关键字段：`id`、`name`、`role`、`status`、`password_hash`、`created_at`、`updated_at`、`version`。

调整：普通 `member` 也允许创建登录会话；用户名和密码都可通过受控接口修改。

#### `sessions`

由现有 `admin_sessions` 演进而来，保存所有后台用户会话。

关键字段：`id`、`member_id`、`token_hash`、`expires_at`、`ip`、`user_agent`、`last_seen_at`、`created_at`。

不在会话表复制角色；每次鉴权读取用户当前角色和状态，禁用或降级可立即生效。

#### `plans`

套餐的稳定身份和展示信息。

建议字段：

- `id`
- `name`：套餐名称
- `description`
- `status`：`draft | active | archived`
- `current_version_id`
- `created_by`
- `created_at`、`updated_at`、`version`

套餐归档后不可再新分配，但既有订阅按原版本继续运行，除非管理员主动撤销。

#### `plan_versions`

套餐不可变配置快照。已发布版本禁止原地修改；编辑套餐时创建新版本。

建议字段：

- `id`、`plan_id`、`version_number`
- `daily_limit_usd`、`weekly_limit_usd`、`monthly_limit_usd`
- `concurrency_limit`
- `max_keys`
- `allowed_models`
- `default_validity_days`
- `timezone`，默认 `Asia/Shanghai`
- `created_by`、`created_at`

额度语义：

- `NULL`：该周期不限制。
- `0`：该周期禁止产生用量。
- 正数：该周期的内部美元上限。
- 所有金额继续使用 `NUMERIC(30,12)`，禁止浮点累计。

#### `plan_pool_bindings`

套餐版本与账号池的多对多关系。

建议字段：`plan_version_id`、`pool_id`、`priority`、`created_at`。

套餐有多个池时按 `priority` 从小到大处理；同优先级池共同形成候选集。

#### `user_subscriptions`

用户实际获得的一份订阅。用户拥有多个套餐，表现为多条订阅记录。

建议字段：

- `id`、`member_id`、`plan_version_id`
- `status`：`scheduled | active | suspended | expired | revoked`
- `starts_at`、`expires_at`
- `daily_limit_override`、`weekly_limit_override`、`monthly_limit_override`
- `concurrency_override`、`max_keys_override`、`allowed_models_override`
- `assigned_by`、`assigned_at`、`notes`
- `created_at`、`updated_at`、`version`

有效配置按“订阅覆盖值优先，否则使用套餐版本值”计算。覆盖值仍不能绕过系统级安全策略。

额度、并发和 Key 数量覆盖值可以由管理员上调或下调，并必须写入管理审计；模型覆盖默认只能收窄套餐版本允许的模型集合，如需扩展模型应发布新的套餐版本。

默认不允许同一用户同时存在两个相同套餐的有效订阅；到期或撤销的历史记录保留，可再次分配。

#### `account_pools`

产品层将现有“账号组”统一改称“账号池”。第一阶段可继续复用 `account_groups` 表，接口和代码逐步更名，兼容稳定后再决定是否物理改表名。

建议字段：

- `id`、`name`、`description`
- `strategy`：`round_robin | weighted_round_robin | priority_failover`
- `status`：`active | disabled`
- `created_at`、`updated_at`、`version`

#### `account_pool_members`

由现有 `account_group_members` 演进。

建议字段：`pool_id`、`account_id`、`weight`、`priority`、`status`、`created_at`。

- 轮询：健康账号依次使用。
- 权重轮询：按 `weight` 分配机会，同时跳过不可用或并发已满账号。
- 优先级故障切换：先使用最小 `priority` 层，整层不可用时才进入下一层。

#### `user_account_grants` 与 `user_pool_grants`

保存管理员对用户的额外资源授权。

建议字段：`id`、`member_id`、目标 ID、`priority`、`status`、`starts_at`、`expires_at`、`assigned_by`、`notes`、`created_at`。

默认优先级为 50，套餐池默认优先级为 100，因此显式分配默认优先，但管理员可以调整。它们只增加路由候选，不增加所选订阅的额度。

#### `api_keys`

调整：

- 新增非空 `user_subscription_id`。
- `member_id` 保留，便于鉴权和查询，但必须与订阅所属用户一致。
- 新创建 Key 的 `client_id` 固定为 `NULL`，后续移除该列。
- `allowed_models` 表示用户主动收窄后的模型集合。
- `concurrency_limit` 不得超过订阅有效并发上限。
- 可新增 `last_used_at`，改善用户侧管理体验。

Key 数量上限统计 `active` 和 `paused` Key；已 `revoked` 的 Key 不再占用名额，但记录永久保留。

不允许直接把既有 Key 改绑到另一订阅，因为这会改变额度和路由含义。用户应创建新 Key，再撤销旧 Key。

#### 请求与账本

`requests` 和 `usage_ledger` 增加 `user_subscription_id`，保存请求发生时的订阅归属，便于多套餐分别统计。

`budget_policies` 增加 `subscription` 作用域与 `owner_subscription_id`，`period` 增加 `month`。分配订阅时，根据日、周、月限制建立对应预算策略，继续复用当前原子预留、结算、释放和未知用量处理。

## 5. 套餐版本与变更规则

套餐必须区分“展示名称”和“已发布配置”，避免管理员编辑套餐后无提示地改变现有用户权益。

工作规则：

1. 新套餐先保存为草稿。
2. 发布时生成 `plan_versions` 记录并设为当前版本。
3. 已发布套餐再次编辑时，创建下一版本，不覆盖旧版本。
4. 新分配订阅默认使用当前版本。
5. 既有订阅继续使用原版本。
6. 管理员可执行“升级订阅版本”，系统先展示额度、模型、并发和池绑定差异。
7. 降低额度时若当前已用量超过新额度，升级操作需要二次确认；升级后立即禁止新请求，但不回滚历史用量。
8. 账号池内部增删账号属于运维动作，实时影响所有引用该池的套餐，不创建套餐新版本。

## 6. 详细产品工作流程

### 6.1 登录与角色分流

1. 用户在统一登录页输入用户名和密码。
2. 服务验证密码、用户状态和登录限流，不再限定只能是管理员。
3. 创建通用会话，返回当前用户 ID、用户名和角色。
4. 管理员进入管理控制台；普通用户进入个人控制台。
5. 前端菜单按角色生成，后端仍逐接口校验权限，不能只依赖隐藏菜单。
6. 用户被禁用、角色变化或密码重置后，旧会话在下一次请求时立即失效。

### 6.2 管理员创建与维护用户

创建用户：

1. 管理员进入“用户管理”，点击“创建用户”。
2. 填写用户名、初始密码、角色和状态。
3. 前端即时校验用户名格式、密码长度和两次密码一致。
4. 后端再次校验唯一性和密码规则，保存 bcrypt 哈希。
5. 创建成功进入用户详情页，可继续分配套餐或额外账号资源。

编辑用户：

- 可修改用户名、角色和状态。
- 可重置密码；密码字段绝不回显。
- 禁用用户会立即阻止登录和所有 Key 调用，但不删除历史账本。
- 用户详情集中展示订阅、Key、额外账号授权、额度和最近用量。

### 6.3 上游账号接入流程

账号页采用 CPA 式向导，避免要求管理员直接理解 Token 字段。

1. 点击“添加上游账号”。
2. 选择接入方式：
   - `OAuth 授权`：推荐方式。
   - `手工凭证`：仅用于已有 Access Token / Refresh Token 的运维场景。
3. OAuth 方式：
   - 选择新账号或重新授权已有账号。
   - 服务创建短期 OAuth 会话并生成授权链接。
   - 前端打开授权页，并在当前页面轮询状态。
   - 回调成功后加密保存凭证，自动生成账号记录。
   - 页面展示成功、失败、超时和可重试状态。
4. 手工方式：
   - 填写标签、Access Token、可选 Refresh Token、上游 Account ID、过期时间和出口策略。
   - 凭证只在创建时输入，之后永不回显。
5. 创建后进入账号详情，显示状态、凭证到期、并发、优先级、出口、所属池和隔离原因。
6. 支持暂停、重新授权、修改标签/并发/出口以及处理隔离；不允许直接查看原始凭证。

### 6.4 创建与维护账号池

1. 管理员进入“账号池”，点击“创建账号池”。
2. 填写名称、说明和调度策略。
3. 从可搜索账号列表中多选账号，不再手工输入 UUID。
4. 根据策略填写成员参数：
   - 轮询：无需权重，允许设置展示顺序。
   - 权重轮询：为每个账号设置权重。
   - 优先级故障切换：为每个账号设置优先级层。
5. 保存前显示健康账号数、总并发和潜在问题，例如池为空、全部暂停或凭证即将过期。
6. 池详情显示账号状态、当前并发、最近错误和被哪些套餐引用。
7. 从池中移除账号前展示影响的套餐数量；确认后新请求立即不再选择该账号，进行中的请求不强制中断。

### 6.5 创建和发布套餐

套餐采用四步向导：

1. 基本信息：名称、说明、默认有效天数。
2. 额度与权限：日/周/月美元额度、并发上限、Key 数量上限、允许模型、时区。
3. 账号池：选择一个或多个账号池并设置池优先级。
4. 确认发布：展示完整权益摘要和风险校验。

发布校验：

- 至少绑定一个启用账号池，或者明确允许仅依赖用户额外授权；默认要求至少一个池。
- 至少设置一个有效额度周期；如全部无限需管理员二次确认。
- 并发和 Key 数量必须为正整数。
- 允许模型必须存在于已激活价格版本中，否则不能启用严格预算。
- 账号池为空或无健康账号时可以保存草稿，但不能发布为可分配版本。

### 6.6 给用户分配多个套餐

1. 在用户详情点击“分配套餐”。
2. 选择一个当前已发布套餐版本。
3. 设置开始时间、到期时间和备注。
4. 可选填写额度、并发、模型和 Key 数量覆盖值。
5. 页面展示用户现有订阅，避免重复分配。
6. 后端在同一事务中创建订阅实例及相应预算策略。
7. 开始时间未到则为 `scheduled`；进入有效期后为 `active`。
8. 分配成功后，该套餐出现在用户个人控制台，并可在创建 Key 时选择。

管理动作：

- 延期：只修改 `expires_at`，保留已用额度。
- 暂停：立即阻止该订阅下所有 Key 新请求。
- 恢复：在有效期内恢复使用；额度不会自动清零。
- 重置额度：按选定周期重置，必须记录操作人、原因和前后值。
- 撤销：永久终止该订阅，所属 Key 自动失去调用资格但保留记录。
- 升级版本：显示差异后迁移到新套餐版本，按明确规则处理当前额度窗口。

### 6.7 给用户额外分配账号或账号池

1. 管理员在用户详情进入“额外资源”。
2. 选择“单个账号”或“账号池”。
3. 选择资源、优先级、开始/到期时间并填写备注。
4. 授权生效后，用户所有有效订阅 Key 的候选路由增加该资源，但额度仍记入每个 Key 所选订阅。
5. 撤销授权后，新请求立即移除该候选；正在执行的请求正常结算。

### 6.8 用户创建 Key 并选择套餐

1. 用户进入“我的 Key”，点击“创建 Key”。
2. 第一步选择订阅。页面只展示自己的 `active` 订阅卡片，包括：
   - 套餐名与版本
   - 到期时间
   - 日/周/月已用与剩余
   - 并发上限
   - 允许模型
   - 已创建 Key 数 / Key 上限
   - 当前账号池可用状态摘要
3. 第二步填写 Key 名称、Key 到期时间、并发和允许模型。
4. 前端只提供订阅允许范围内的选项；后端再次校验：
   - 订阅归属于当前用户且有效。
   - 当前活跃 Key 数未达到该订阅上限。
   - Key 到期时间不得晚于订阅到期时间。
   - Key 并发不得超过订阅有效上限。
   - Key 模型必须是订阅允许模型的子集。
5. 在事务中创建 Key，并绑定 `user_subscription_id`。
6. 完整密钥只显示一次，页面要求用户复制后确认关闭。
7. 后续列表只显示名称、前缀、所属套餐、状态、创建时间、最后使用时间和用量。

Key 状态操作：

- 暂停可恢复。
- 撤销不可恢复。
- 订阅暂停或过期不会篡改 Key 自身状态；订阅恢复后，仍为 `active` 的 Key 可继续使用。
- 订阅撤销后 Key 永久不可用，建议用户重新选择有效订阅创建新 Key。

### 6.9 请求鉴权、路由与额度扣减

每次请求按以下顺序执行：

1. 校验 API Key 哈希、Key 状态和 Key 有效期。
2. 加载 Key 所属用户，验证用户为启用状态。
3. 加载 Key 绑定的订阅，验证归属关系、状态和有效期。
4. 加载订阅对应的不可变套餐版本及覆盖配置。
5. 校验请求模型在 Key 与订阅允许模型交集内。
6. 解析候选路由：
   - 套餐版本绑定的有效账号池；
   - 用户当前有效的额外账号授权；
   - 用户当前有效的额外账号池授权。
7. 如果没有候选路由，返回 `no_eligible_upstream`，不进入上游。
8. 完成本地规则和官方 Moderation 前置审核。
9. 审核完成后绕过缓存，再次校验 Key、用户、订阅、套餐版本和路由授权。
10. 按 Key、订阅和账号三层并发限制原子取得执行名额。
11. 根据池优先级和池内策略选择健康且未满载的账号；会话黏性只允许命中当前候选集中的账号。
12. 对订阅日/周/月预算及既有账号/池预算同时做原子预留；任一限制不足则全部回滚。
13. 调用上游并流式返回。
14. 按请求的冻结价格版本结算到订阅、Key、账号和池维度。
15. 释放并发名额；用量未知时保留预留并进入现有人工处置流程。

候选账号即使来自用户额外授权，也始终消耗当前 Key 所选订阅的额度，不形成绕过套餐额度的路径。

### 6.10 套餐周期和额度规则

- 日周期：按订阅时区的自然日重置。
- 周周期：默认周一 00:00 重置。
- 月周期：每月 1 日 00:00 重置。
- 若同时配置日、周、月额度，三个窗口都必须有余额。
- 周期开始时冻结额度快照；套餐池增减账号不会改变当前额度。
- 管理员修改订阅覆盖值时，默认只影响下一周期；选择“立即生效”必须记录审计事件。
- Key 之间共享订阅余额，不能通过创建多个 Key 获得多份额度。
- 到期订阅不自动续期；续期由管理员延期或重新分配。

## 9. 兼容迁移方案

迁移采用“先增加、后切换、最后清理”，避免一次发布同时破坏登录、Key 和请求路由。

### 阶段 A：增加新结构

1. 新增套餐、套餐版本、订阅、套餐池绑定和用户额外授权表。
2. 给 `api_keys`、`requests`、`usage_ledger` 增加可空的 `user_subscription_id`。
3. 扩展预算策略支持订阅作用域和月周期。
4. 将 `admin_sessions` 扩展或迁移为通用会话表。
5. 保留现有客户端、Key 路由和账号组结构，暂不删列。

### 阶段 B：兼容旧 Key

对每个旧 Key 读取其 `key_routes`：

1. 为其路由集合创建隐藏的“迁移账号池”。
2. 创建隐藏且禁止新建 Key 的“Legacy 导入套餐版本”。
3. 为原 Key 所属用户创建迁移订阅，并回填 `user_subscription_id`。
4. 旧预算策略继续生效，迁移订阅不重复创建额度，避免双重扣减。
5. 保存迁移映射和审计记录，允许按 Key 追溯。

如果数据库实际没有旧业务 Key，可跳过 Legacy 数据生成，但迁移脚本仍需支持非空生产数据。

### 阶段 C：后端双读与新接口

1. 会话鉴权支持管理员和普通用户。
2. 新 Key 强制绑定订阅，并走动态订阅路由。
3. 旧 Key 在迁移完成前仍可回退读取 `key_routes`。
4. 请求、账本和管理事件补充订阅归属。
5. 完成新旧路径回归后，将 `user_subscription_id` 改为非空。

### 阶段 D：前端切换

1. 上线角色化导航和个人控制台。
2. 上线用户详情、套餐、订阅、账号池和账号向导。
3. 从导航移除“客户端”和独立“OAuth 会话”。
4. 禁止前端创建带 `client_id` 的 Key。

### 阶段 E：清理兼容层

1. 观察至少一个完整最长额度周期并确认没有旧调用路径。
2. 停用旧 `/clients` 与手工 `key_routes` 管理接口。
3. `clients` 表和 `api_keys.client_id` 暂时保留只读，下一次破坏性迁移再删除。
4. 数据库 `account_groups` 的物理更名可单独安排，不与业务切换捆绑。

## 10. 建议开发顺序

### P1：数据结构与领域服务

- 新增迁移和实体约束。
- 实现套餐版本、订阅状态、有效配置计算。
- 扩展预算周期到月，并接入订阅作用域。
- 完成旧 Key 迁移和幂等回滚测试。

完成标准：数据库可表达全部关系，迁移可重复执行且旧 Key 权限不扩大。

### P2：统一登录与权限隔离

- 将管理员专用会话改成通用会话。
- 实现管理员、本人资源两类授权中间件。
- 实现修改密码、重置密码和会话撤销。
- 加入最后一个管理员保护。

完成标准：普通用户可登录但无法访问任何管理员接口；越权测试全部返回 403/404。

### P3：套餐、订阅与额外授权 API

- 完成套餐草稿、发布、版本升级。
- 完成订阅分配、延期、暂停、恢复、撤销和额度重置。
- 完成用户单账号/账号池授权。

完成标准：管理员无需操作数据库即可完成完整资源分配。

### P4：用户 Key 与动态请求链

- Key 创建强制选择订阅。
- 实现动态路由解析和审核后二次校验。
- 增加 Key、订阅、账号三层并发。
- 请求与账本按订阅归属。

完成标准：多套餐额度独立，同一订阅多 Key 共享额度，撤销订阅立即阻止旧 Key。

### P5：上游账号与账号池体验

- 将 OAuth 会话并入账号接入向导。
- 完成账号详情和重新授权。
- 完成账号池多选编辑、策略配置和影响提示。

完成标准：日常账号和池管理不再要求手工复制 UUID。

### P6：管理员与用户前端

- 重做角色化外壳和导航。
- 实现用户详情、套餐向导、订阅管理、账号池详情。
- 实现个人订阅卡片、Key 创建向导、用量页和账户安全页。
- 移除客户端入口。

完成标准：管理员和普通用户分别完成端到端任务，无需调用 API 或数据库。

### P7：迁移演练与上线

- 使用生产数据副本执行迁移演练。
- 对比迁移前后每个 Key 的用户、候选账号和预算范围。
- 灰度开启新请求链，监控鉴权失败、无路由和额度拒绝。
- 保留回退开关，稳定后关闭旧路由。

完成标准：没有 Key 获得超出迁移前范围的账号权限，账本金额一致，旧客户端概念不再出现在用户流程。

## 11. 测试与验收清单

### 用户与安全

- 管理员能修改自己的用户名和密码。
- 管理员能重置普通用户密码，旧会话全部失效。
- 普通用户修改密码需验证旧密码，其他会话失效。
- 普通用户不能查看或修改其他用户、账号、账号池和套餐。
- 不能禁用或降级最后一个启用管理员。

### 多套餐与 Key

- 同一用户同时拥有两个有效订阅，并能在创建 Key 时正确选择。
- Key A 绑定套餐 A、Key B 绑定套餐 B，额度和用量分别累计。
- 同一订阅创建多个 Key 时共享额度，不重复获得额度。
- Key 参数不能超过套餐模型、并发、到期和数量限制。
- 暂停、到期或撤销订阅后，所属 Key 立即按规则失效。
- 套餐升级不会无提示改变旧订阅。

### 账号池与路由

- 单账号池可正常调度。
- 多账号池按池优先级工作。
- 轮询、权重轮询和优先级故障切换结果符合配置。
- 账号在多个池中不会在一次候选集中重复计算。
- 暂停账号、移出池或撤销额外授权后，审核后二次校验能阻止旧候选继续使用。
- 会话黏性不能把请求送到当前已无权限的旧账号。

### 额度与账本

- 日、周、月周期边界按时区正确计算。
- 多个周期同时配置时，任一超限都拒绝。
- 并发预留下额度不超卖。
- 请求成功、失败、取消、断流和未知用量都正确结算或保留。
- 用户额外账号授权不绕过订阅额度。
- 金额全程使用定点数，迁移前后账本总额一致。

### 迁移

- 迁移脚本可在空库和有旧 Key 的数据库执行。
- 同一迁移重复运行不生成重复套餐、池或订阅。
- 每个旧 Key 的候选账号集合迁移后不得扩大。
- 回滚不会丢失原 `key_routes`、`client_id` 或预算数据。

## 12. 上线观察指标

- 登录成功/失败与会话撤销数量。
- 活跃用户、活跃订阅、各套餐 Key 数。
- 按订阅统计已用、预留和剩余额度。
- `subscription_inactive`、`subscription_quota_exceeded`、`no_eligible_upstream` 错误率。
- 每个账号池健康账号数、满载率、故障切换次数。
- OAuth 成功、失败、超时和重新授权数量。
- Legacy Key 请求占比；降为零后才能清理旧路由。

## 13. 明确不在本轮范围内

- 用户公开注册、找回密码邮件、短信验证码。
- 在线支付、自动续费、充值和兑换码。
- 用户自行购买套餐。
- 多租户组织、团队邀请和子管理员。
- 向普通用户公开上游账号身份、真实余额或 OAuth 凭证。
- 强制中断已经发送到上游的进行中请求。

## 14. 参考实现取舍

- CPA：借鉴 OAuth/凭证接入向导、状态轮询、重新授权和账号可观测性，不照搬文件式凭证存储。
- Sub2API：借鉴账号分组、用户订阅实例、日/周/月额度窗口及订阅管理动作。
- 不照搬 Sub2API 的 Key 权限快照方式；本项目每次请求动态校验 Key 所选订阅及当前账号池授权，避免旧 Key 权限漂移。
- 保留 SubAI 现有严格预算预留、冻结价格版本、未知用量保留和审核后二次校验能力。

## 15. 方案评审结论

同一个用户默认不能同时拥有两份“同一套餐”的有效订阅，以避免创建 Key 时难以区分相同名称、相同权益但额度独立的两份订阅。如果未来需要叠加购买，可在订阅展示名中加入批次和到期时间后放开该约束。
